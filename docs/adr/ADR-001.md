# ADR-001: Separate Calculation Logic from Interface Concerns

## Context

During the design of my Three-Phase Power Calculator, I needed to decide how the calculation logic should be separated from the parts of the application that collect and display information.

The calculator is intended to handle balanced three-phase calculations using information such as voltage, current, power factor, connection type, voltage basis, and the requested output. As the domain model developed, I considered whether the electrical equations should be placed directly with the interface logic or separated into their own service.

This decision matters because placing the equations directly in the interface would make the first version simpler, but it would also connect the electrical calculations to a specific way of interacting with the application.

## Decision

I decided to separate the calculation logic from the interface and represent the calculation flow using:

`CalculationRequest → CalculationService → CalculationResult`

`CalculationRequest` represents the information needed to perform a calculation. `CalculationService` is responsible for validating the request and applying the appropriate three-phase equations. `CalculationResult` represents the result returned by the calculation, including information such as the calculated value, unit, quantity, formula label, and assumptions.

This keeps the calculation logic independent from the interface used to collect or display the data.

## Alternatives Considered

### Alternative 1: Put the calculation equations directly in the interface code

One option was to perform the calculations directly in the same part of the application that collects user input and displays the result.

I did not choose this because it would tightly couple the electrical equations to the interface. This would make the calculation logic harder to test independently and would make changing the interface later more difficult.

Although this approach would require less structure initially, I decided that separating the calculation logic was worth the additional classes.

### Alternative 2: Create a separate class for every calculation type

Another option was to create different calculation classes for real power, reactive power, apparent power, line-to-phase conversions, and other supported calculations.

I did not choose this because the current calculator does not yet have enough different behavior to justify that many separate classes. Most of the calculations use the same basic inputs and are closely related.

Creating a class for every equation at this stage would add more files and relationships without providing enough benefit for the current scope.

## Consequences

The main benefit of this decision is that the electrical calculation logic can remain independent from the interface. This should make the calculations easier to test and allows another interface to use the same calculation logic later without rewriting the equations.

The request and result objects also make the information entering and leaving the calculation service more explicit.

The downside is that the design now contains more structure than putting everything directly in one interface or calculation class. Information has to be passed through `CalculationRequest`, processed by `CalculationService`, and returned as a `CalculationResult`.

Another consequence is that `CalculationService` could become too large as more calculations are added. If different calculations eventually require substantially different behavior or data, the service may need to be divided into smaller calculation-specific components.

For the current scope, I am accepting that risk rather than creating separate calculation classes before they are necessary.
